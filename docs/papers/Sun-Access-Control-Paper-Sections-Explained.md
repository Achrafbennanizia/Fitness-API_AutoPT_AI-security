# Section-by-section explanation of Sun, Xu, and Su (USENIX Security 2011)

Paper title: *Static Detection of Access Control Vulnerabilities in Web Applications* (Fangqi Sun, Liang Xu, Zhendong Su, UC Davis). Venue: 20th USENIX Security Symposium, 2011.

This is a reading companion, not an attack playbook. The paper’s object is **missing or insufficient access checks** on web pages: a less-privileged role can open a URL that the UI never offered. That is the ancestor of today’s broken object-level authorization story, told with static analysis and sitemaps rather than with an LLM.

**What this paper supports in the semester project:** the **core bug class** on multi-user fitness apps — one account reaching another account’s objects (workout IDs, GPX, plans, metrics). It grounds the AI-locked class (if that class is access control) and the hardening pass in 2011 USENIX science, not only in OWASP slogans. It does **not** put Semgrep or white-box SAST into your empirical protocol; Peng already set white/grey out of the bake-off. You cite Sun for *what the bug is*, not for *how you will scan*.

## Abstract

Access-control bugs cause privilege escalation. They are hard because, unlike XSS or SQLi, they are **application-specific**: there is no single sanitizer to check. Manual specs are tedious and wrong. Probabilistic spec inference is expensive and fuzzy. Sun et al. offer what they call the **first static analysis** that infers **implicit** access-control assumptions from the app itself and then checks them.

The insight is almost sociological. Source and templates already *document* who is supposed to see which link. If role A’s page shows “delete user” and role B’s page does not, that page is privileged. If role B can still **force-browse** the URL and get the same HTML, the check is missing. The analysis therefore (1) builds a **per-role sitemap** of explicit links, (2) subtracts sitemaps to find privileged nodes, (3) simulates a direct request as the weaker role, (4) flags pages whose response looks like the stronger role’s.

They implement this on PHP, run it on real apps, and report known plus new bugs with few false positives, at usable scale. For 2026 students the abstract is a definition of **success** you can reuse without running their OCaml analyser: two synthetic accounts, an object URL the UI hides from the weaker account, a response that still returns the object. That HTTP pair is your evidence row. Their static trick is how they *found* such rows in PHP apps before deployment. Your black-box tools have to find the same *class* from the outside.

## 1 Introduction

Web apps restrict privileged operations and then get the restriction wrong. HTTP is stateless, so every request must re-identify the user; that is a perennial source of missing checks. A 2007 WASC-style statistic they cite put insufficient authorization around 14% of surveyed apps. Injection got more research because it has a general definition (untrusted flow into a sink). Access control requires looking at **connections between pages**, not one page in isolation.

They illustrate “security by obscurity” with public incidents (predictable member-only file URLs; earnings data leaked hours early; conference videos with guessable names). The lesson is not the incidents. The lesson is: **hiding a link is not an access check.** Dynamic crawlers miss hidden pages and intended role maps; they are also shallow. Prior static tools wanted specs that nobody writes. So Sun et al. infer intended access from **explicit links shown to each role**, then test whether a weaker role can still open the privileged node.

Contributions they list: a formal definition; a role-based static analysis with little manual spec (entry points + role state); an implementation that builds per-role sitemaps and explores feasible paths; an evaluation on unmodified real apps. Roadmap: example (§2), formalism (§3), algorithms (§4), implementation (§5), evaluation (§6), related work (§7), conclusion (§8).

For five fitness apps, §1 is why Alice-and-Bob *stories* (two accounts, object IDs) are the right unit even though you deleted the names. It is also why a scanner that only looks for reflected XSS will miss the thing Papageorgiou-style privacy papers and OWASP API1 both worry about.

## 2 Illustrative example

Figure 1 is a tiny PHP app with two roles: administrator `a` and normal user `b`. Specs the developer must provide are small: both roles enter at `index.php`; session flag `admin` is true for `a` and false for `b`. Only `functions.php` contains the check. `index.php` and `user_delete.php` include it. **`user_add.php` does not.**

Sitemap construction is a worklist. For role `a`, `index.php` exposes links to add and delete plus the include; the worklist drains through those nodes. For role `b`, the check hides the add/delete anchors, so the sitemap has almost nothing. Privileged pages are the set difference: add and delete. Forced browsing as `b`: delete is blocked (check runs); add succeeds (no check). That single missing include is the bug.

You will not run this analyser on Workout.cool. You *will* look for the same shape from HTTP: a control that user A sees and user B does not, plus a URL that still works as B. Semgrep could find a missing middleware in grey-box — out of your empirical scope. ZAP/Nuclei/HITL have to notice IDOR-shaped status codes instead. The example is the **picture** to put in the report’s background when you explain authorization, not a PHP homework.

## 3 Approach formulation

This section is the math so later algorithms have nouns. **Role:** a set of allowed accesses; roles form a lattice (public ⊥, user in the middle, admin ⊤). Accessing a higher node’s resource as a lower role is privilege escalation. **Explicit link:** a URL actually emitted in HTML/includes/redirects/frames/etc. without error. **Forced browsing:** opening a privileged URL without following an explicit link; success means the HTML (and redirects) look like the privileged role’s. **Web application** for a role: entries, states, explicit edges, implicit edges, navigation paths, explicitly reachable nodes. **Assumption 2:** if several roles can *explicitly* reach a node, required privilege is that of the **least** privileged of them — so a page linked for both is not “admin-only” unless the developer overrides. **Definition 5:** node `n` is vulnerable if it is explicitly reachable for stronger role `a`, not for weaker `b`, yet some allowed (possibly implicit) path for `b` still contains `n`.

Two warnings for 2026. First, object-level bugs in REST APIs are often **same role, different object** (user 12 vs user 13), not only admin vs user. Sun’s lattice still helps, but you must treat “user A’s objects” vs “user B’s objects” as the roles that matter. Second, their success criterion (HTML equality / no redirect) is a 2011 HTML-app proxy. JSON APIs need **status code + body identity** instead. Translate, do not copy.

### 4.1 Vulnerability detection

`DETECTVULS` takes specs for roles `a` and `b` and a regex of HTML tags that can carry links. Regex → NFA → DFA (they prefer DFA). Build sitemaps; privileged = Na \ Nb. For each privileged node, build a context-free grammar approximating HTML for `a` and for `b`, plus redirect sets. If CFG sizes and redirects match, the weaker role saw the same page → flag. If they differ (login form, error, extra redirect), the page is considered guarded.

False-positive logic is in that equality test: two roles might get coincidentally similar error pages. They claim few FPs in §6. False negatives include pages that *are* linked for the weak role but still should have been admin-only (Assumption 2); developers may list extra privileged nodes by hand.

Your black-box version: two sessions, same URL with another user’s id, compare status/body. No CFG required. The algorithm is the ancestor of that pairwise comparison.

### 4.2 Building sitemaps

Worklist BFS from role-specific entries. For each page, construct a CFG of possible HTML under that role’s state, extract links, add redirects and includes as edges, enqueue unseen **active** nodes (PHP pages, not PDFs). Includes are treated conservatively because an included file might still show a sensitive widget. Inactive nodes are dead ends.

This is why dynamic crawlers disappointed them: they never *see* the admin-only anchor, so they never add the edge, so they never test the URL. Static per-role sitemaps see the anchor in the `if (admin)` branch when the spec sets admin true.

Out of empirical scope for you (white-box). Conceptually: your HITL agent is a *dynamic* crawler with a model proposing IDs to try. Sun is the static completeness argument for why IDOR exists even when the UI is clean.

### 4.3 Link extraction

Naive approach: intersect CFG with a language of “HTML that contains a link tag,” enumerate strings, parse HTML. Two problems: infinitely many strings, and millions of near-duplicates. Their algorithm walks the CFG in lockstep with a DFA that matches link-introducing tags, accumulating only matched URL strings, resetting on mismatch, discarding `Σ*` links that could be anything. `VQW` memoisation guarantees termination.

You do not implement this. You need one idea: **the HTML the server would emit already contains the intended map of the app.** Fitness SPAs may put that map in JavaScript JSON rather than `<a href>`. The 2011 DFA will miss those. Your black-box tests still compare **object URLs**, which survive the SPA era.

### 5.1 Specification rules

Developers specify, per role, **entry set** and **critical state** (session, cookies, selected request params, etc.). Entries can be shared. Optional: explicitly mark privileged nodes to catch Assumption-2 false negatives. Function return values can be pinned by file:line. This is “minimal spec,” not “no spec.” Your analog is: two registered users and the knowledge that both can log in — still black-box, because registration is a public flow.

### 5.2 Sitemap builder

**5.2.1 CFG constructor.** AST → IR; path-sensitive exploration; skip infeasible branches (`admin` false ⇒ do not emit add-user anchor). HTTP parameters default to `Σ*` unless specified, so each page is analysed once (scale over precision). Include-path resolution follows PHP’s search order. The `checkUser()` example shows Z3 proving a branch dead so `SensitiveOperation()` is not explored for the weak role.

**5.2.2 Link extractor.** Only in-app links; the DFA example matches `a`/`form`/`iframe` tags. A `$lang`-dependent anchor shows why CFGs have several productions for one echo.

None of this is your scanner. It is why a **missing middleware on one REST handler** is the 2026 version of `user_add.php` forgetting to include `functions.php`. Hardening = put the check on every handler that touches an object ID, not only on the ones the UI links.
